### Key-to-frame latency: haetty-v0.4.0 against main (the person's question)

PX's report gave 25 ms key to frame; DESIGN §3.4's budget table gives 0.96 ms. Both builds measured the same way on
kramers, 2026-11-22: the `dist` profile, `scripts/e2e/measure.sh` under Xvfb (its Claude Code case skipped: no
`claude` on its PATH, the installed claude is not started by tests), and PX's own method (`/home/kim/m4/pd/kf.sh`:
`xdotool type` one key into a plain shell, wait until the dumped frame file changes; 60 keys, two runs each). v0.4.0
was built from `haetty-v0.4.0` in its own worktree and target folder; main was `03b6d60` (the same code as
`ec3e923`, 0.4.1).

| | v0.4.0 (`b1fd31b`) | main (0.4.1) |
|---|---|---|
| key → frame through the daemon (`examples/latency.rs`, 300 keys), in measure.sh | median 3.03 ms, p95 6.73 | median 1.76 ms, p95 6.26 |
| the same, five runs each, taken in turn | medians 5.97, 5.40, 1.84, 4.37, 6.08 ms; p95 5.90–6.70 | medians 5.87, 4.80, 2.54, 5.63, 6.03 ms; p95 6.56–6.66 |
| GUI draw per incremental frame while typing (trace log) | median 0.63 ms, p95 1.38 | median 0.80 ms, p95 1.09 |
| PX's method: key → dumped frame | medians 49.3, 42.6 ms | medians 18.5, 35.9 ms |
| the `xdotool` process alone, in that loop | medians 9.4, 10.9 ms | medians 3.4, 9.4 ms |
| throughput plain / wrapped / SGR (MiB/s) | 11 / 23 / 23 | 11 / 23 / 24 |
| idle GUI + daemon, 1/2/4 tabs, scrollback filled | 0 ticks in 30 s; GUI 7.5 / 8.8 / 9.6 MB | 0 ticks; GUI 7.5 / 8.8 / 9.7 MB |

Result: no slowdown; the two builds have the same distribution (the daemon path is bimodal on kramers, about 2 ms or
about 6 ms, in both). The numbers differ for two reasons, both of method:

- The budget table's 0.96 ms was measured on the earlier development machine (Linux under WSL2, before 2026-11-10);
  on kramers (a ThinkPad T480 on battery-managed clocks, with the stable instance and this session running) the same
  example gives 1.8–6 ms, and the throughput lines are about half the table's (11 against 24 MiB/s), so the machine
  explains the factor.
- PX's 25 ms is a different quantity: it starts an `xdotool` process per key (3–11 ms by itself), goes through
  `/bin/sh`'s echo in a PTY, and ends when the GUI has written a full PPM frame dump to disk (`HAETTY_DUMP_FRAME`, a
  test-only path). It is fit for comparing cases inside one run (what PX did), not for the budget.
