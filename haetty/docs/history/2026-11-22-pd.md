### Key-to-frame latency: haetty-v0.4.0 against main (the person's question)

PX's report gave 25 ms key to frame; DESIGN §3.4's budget table gives 0.96 ms. Both builds measured the same way on
kramers, 2026-11-22: the `dist` profile, `scripts/e2e/measure.sh` under Xvfb (its Claude Code case skipped: no
`claude` on its PATH, the installed claude is not started by tests), and PX's own method (`/home/kim/m4/pd/kf.sh`:
`xdotool type` one key into a plain shell, wait until the dumped frame file changes; 60 keys, two runs each). v0.4.0
was built from `haetty-v0.4.0` in its own worktree and target folder; main was `03b6d60` (the same code as
`ec3e923`, 0.4.1).

|---|---|---|

| the same, five runs each, taken in turn | medians 5.97, 5.40, 1.84, 4.37, 6.08 ms; p95 5.90–6.70 | medians 5.87, 4.80, 2.54, 5.63, 6.03 ms; p95 6.56–6.66 |

Result: no slowdown; the two builds have the same distribution (the daemon path is bimodal on kramers, about 2 ms or
about 6 ms, in both). The numbers differ for two reasons, both of method:

- The budget table's 0.96 ms was measured on the earlier development machine (Linux under WSL2, before 2026-11-10);
  on kramers (a ThinkPad T480 on battery-managed clocks, with the stable instance and this session running) the same
  example gives 1.8–6 ms, and the throughput lines are about half the table's (11 against 24 MiB/s), so the machine
  explains the factor.
- PX's 25 ms is a different quantity: it starts an `xdotool` process per key (3–11 ms by itself), goes through
  `/bin/sh`'s echo in a PTY, and ends when the GUI has written a full PPM frame dump to disk (`HAETTY_DUMP_FRAME`, a
  test-only path). It is fit for comparing cases inside one run (what PX did), not for the budget.

## D1–D3. As built

- The daemon keeps each session's newest 64 edits in Claude Code's shape (`haetty-cc::patch`): PostToolUse's
  `structuredPatch` of Edit and Write, and before it, from PreToolUse, the snapshot's hunks against the tool input
  (three lines of context, a tab as two spaces; a new file and a secret-looking file give none). `GetPatches` on
  `GetClaude`'s line; `ClaudeInfo::patch_gen` (protocol 20).
- The window (`inline_diff.rs`, `app_inline.rs`): for the active Claude Code tab, when `patch_gen` changes it reads the
  patches; on each new screen it finds candidates (rows with a right-aligned number, a space, a mark; coloured `-`/`+`
  rows, context rows without a background; a long line's next rows joined), matches each against every hunk, keeps
  only a match to exactly one edit, lays it out inside the block's rows and the columns of its background, and paints
  it into the composed frame after it is built. The result is cached by a hash of the screen's text and backgrounds,
  the patches and the turned-back blocks; finding and laying out over 1 ms gives up for that frame.
- Clicks: `⇄` (the header row's last column of the block) turns the block back for the tab's life; the file's name in
  the header opens P3b's overlay on that file. A selection over the block: the side of the drag, whole lines.
- `inline-diff = split | unified` (Claude Code group), `inline-diff-min-cols` (110), palette "Toggle inline diff
  layout" (saved to the config file).

## Choices made, and what was not chosen

- Painted into the composed frame (as the selection is marked) rather than into a copy of the tab's screen: no copy,
  and an overlay is never covered (nothing is painted while one is open).
- Claude Code's own hunks (`structuredPatch`) for blocks after the tool ran; the computed ones only while the tool
  waits. Not chosen: always computing them (a different diff algorithm could pair lines otherwise).
- Words for the deeper tint are whitespace-separated tokens (`similar`'s word diff): `add(a,` against
  `add_numbers(a,`. Finer (characters) costs more and looks noisier.
- The mark goes on the first row above the block that is not blank and not a border (in a question: the file's
  row), only where that row's last cell of the block is blank.
- Not done: the block's turned-back state is not kept across a restart; a key over the block (the text allows a click
  or a key; the click is there).
