| stable scrollback coordinates | none counted; `TrackedGridRef` follows a row through scrolling and pruning and reports when it was pruned | `VecDeque` scrollback: a count of evicted lines added (and ED 3) |

Choice: the selection lives in the GUI and the engines only number and read rows. Reasons: two windows can select
different things in one session (the default the text gives); the mouse never waits for the engine thread; one
implementation of words, lines and text for both engines, so the same table runs on both; libghostty's own selection
would have needed the same work again in haetty-vt. A row's number is `Scrollbar::dropped + offset + y`: the
engine counts the rows it dropped from the top. libghostty: one tracked grid reference on the first row of the
primary screen's active area, read at each snapshot (how far it moved up is what was dropped); if the reference was
pruned itself (more output than the scrollback holds between two snapshots) the count jumps by 2³², so an old number
never reaches a newer row. Neither engine needed a structural change (the stop condition did not apply).

## X1–X3. As built

- `haetty-core`: `Scrollbar::dropped`, `Snapshot::wrapped`, `TextRow`/`TextRows`, `VtEngine::rows`,
  `SessionHandle::rows` (`Cmd::Rows` on the engine thread). Protocol 19: the frame's scrollbar has the count, the frame
  lists the wrapped rows, `GetRows { session, from, count }` → `Rows` (at most 2000 rows; `Secret`, never logged).
  Role table: on `GetClaude`'s line, Control always, Observe only for an observable session. The text said "the
  line of the screen read `haetty screen` uses", but that query (`GetScreen`) is Observe alone; the rule the text
  gives is `GetClaude`'s line, so it went there.
- `haetty-gui`: `selection.rs` (ranges by row number, words, lines, rectangles, the text; no window state) and
  `app_select.rs` (the mouse, the keys, copy, following the rows, marking the composed frame). The bounds are worked
  out when the selection changes, never while drawing (a word or line at the screen's edge may need a row from the
  daemon). A selection on screen is copied at once; one into the scrollback is read on a thread with its own daemon
  connection and handed back as `UserEvent::Copied`, cut at 16 MiB with a hint.
- Keys: Ctrl+Shift+C (`copy`, palette "Copy"; nothing without a selection, never sent). Esc with a selection clears it
  and is not sent (so it does not interrupt Claude Code). Settings (Terminal group, applied at once):
  `copy-on-select = true | false | clipboard`, `selection-clear-on-typing`, `selection-word-chars`.
- Drawing: the `SELECTED` flag the painter already had, with the theme's selection colours and 9625bbd's rule;
  overlay cells (diff, agent record) are marked for an overlay selection only. Reference frames `selection`,
  `selection-rect`, `selection-diff`; no other frame changed.

## Choices made, and what was not chosen

- The selection in the GUI, not in libghostty's selection API (above).
- Alt+drag for rectangles: Ghostty's docs name no key; WezTerm and Windows Terminal use Alt.
- Esc that clears a selection is swallowed: otherwise one Esc both clears and interrupts Claude Code.
- A tab switch, a resize and a switch of screens clear the selection instead of mapping it (reflow moves rows).
- A Shift+click without a selection starts one; a single click on one cell selects nothing.
- Copying from the daemon on a thread with its own connection, not through the window's client (its replies are
  read by whichever request waits, and the window must never wait).
- Not done: libghostty's per-cell reads make a 16 MiB copy take 18 s (the engine thread answers 2000 rows at a time,
  so output keeps flowing between); its formatter could read faster. A proposal, not needed for daily use.
