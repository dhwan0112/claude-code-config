# Stage PU: releases and the in-app update (2026-11-16)

NORTH-STAR conditions (standalone, light) and point 1 (UI). The person's stage text was given in the session (Korean),
parts U0–U7. Approved in advance: the DESIGN §2 change of U5, one HTTPS client and one signature crate chosen from
U0's table, one line in CLAUDE.md (the in-app update is the user's own install, run from the GUI).

## U0. Survey and measurements (before the code)

### The install layout today

- **Linux** (`tools/install-stable.sh`): `<prefix>/.local/opt/haetty/<crate version>-<12-digit commit>/` holds
  `haetty`, `LICENSE`, `THIRD-PARTY-NOTICES.md`, `README.md`, `INSTALLED` (`version=`, `ref=`, `commit=`,
  `installed=`, `source=`); the files and the folder are 0555; it is written as `.<version>.partial` and renamed.
  `<prefix>/.local/bin/haetty` is a symbolic link to the active version's `haetty`, switched atomically (a new link
  renamed over it, `mv -Tf`). Rollback: `--activate VERSION`. `haetty install-desktop` writes
  `~/.local/share/applications/<app id>.desktop` with `Exec=` the path haetty was started by when that resolves to
  itself — the link — so the desktop entry follows updates and rollbacks (`install.rs`, `launcher_path`).
- **Windows** (`tools/install-stable.ps1`): `<prefix>\Programs\haetty\<version>\` (files read-only) and the
  **directory junction** `…\haetty\current` → the active version (Windows has no user-made symbolic links without
  developer mode; a junction needs no privilege). The Start menu shortcut `%APPDATA%\…\Programs\haetty.lnk`, the user
  PATH and a taskbar pin all use `current\haetty.exe`. Rollback: `-Activate VERSION` (the junction removed with
  `rmdir` and made again). The AppUserModelID is set by the executable itself (`main.rs`), so it does not change with
  the version.

### How a running haetty tells its install form (implemented in `haetty_update::layout::detect`)

- (a) versioned: its canonical path is `…/opt/haetty/<version>/haetty` (Windows `…\Programs\haetty\<version>\haetty.exe`)
  with `INSTALLED` beside it; the link is `<prefix>/.local/bin/haetty` (Windows `…\haetty\current`).
- (b) single file: anything else in a folder this user may write.
- (c) dev: `HAETTY_INSTANCE` set, or a path under a cargo `target/{debug,release,dist,<triple>}`.
- (d) no write permission: the versions folder or the link's folder (a), or the executable's folder (b), refuses a
  probe file.

### HTTPS clients (stripped size added to a small baseline binary; haetty's dist profile: opt-level "s", thin LTO)

Measured by a worker in `scratchpad/u0-size/` (15 test crates, both targets, one build at a time). Baseline 315 904 B
(Linux), 270 336 B (Windows).

| candidate | Linux + | Windows + | new Linux libraries | proxy (`HTTPS_PROXY`) | certificates | windows-gnu |
|---|---|---|---|---|---|---|
| ureq 3 + rustls (ring) + bundled roots (webpki-roots) | 1 600 920 | 1 420 288 | none | yes | bundled at build | builds |
| ureq 3 + rustls (ring) + platform verifier | 1 627 264 | 1 378 816 | none | yes | **system store** | builds |
| ureq 3 + rustls (aws-lc-rs) | 2 385 888 | 1 976 832 | none | yes | bundled | builds (C code, no nasm needed) |
| ureq 3 + native-tls | 491 264 | **412 672** | **libssl, libcrypto: out** on Linux | yes | system (Schannel) | builds |
| minreq + rustls (+ `proxy`) | 2 097 296 | 1 725 440 | none | with `proxy` | bundled | builds |
| attohttpc + rustls | 2 455 840 | 2 053 632 | none | yes | (its ring variant loads no roots) | builds |

Windows DLLs added: ring → `advapi32`, `bcrypt`; platform verifier → `crypt32`; Schannel → `secur32`. All system DLLs.
One real GET per client against the GitHub API answered (TLS fine; 404: the repository has no release yet).

Signature and the rest: `minisign-verify` +42 384 / +40 448 B; `ed25519-dalek` + `blake2` +59 952 / +60 416; `sha2`
+12 720 / +12 288; `flate2` + `tar` +120 568 / +110 080; `zip` (deflate) +234 168 / +235 520.

**Chosen:** ureq 3 on each platform's smallest TLS that adds no library — Linux rustls on ring with the system trust
store (the platform verifier: +27 KB over bundled roots, chosen so the trust store follows the distribution's CA
updates and a company's own CA; bundled roots would be frozen at build time), Windows Schannel (native-tls).
`minisign-verify` for signatures. No archive or hash crate: gzip and zip are read with `miniz_oxide` (already in the
binary for PNG) and an own small tar/zip reader; SHA-256 is implemented in `hash.rs` (FIPS 180-4 vectors in its
tests) — the Windows build has no crypto crate to borrow it from. Licences: all permissive (MIT, Apache-2.0, ISC,
BSD-3-Clause; ring Apache-2.0 AND ISC); `THIRD-PARTY-NOTICES.md` lists them.

### GitHub's releases API (official documentation, 2026-11-16)

- `GET /repos/{owner}/{repo}/releases/latest`: "The latest release is the most recent non-prerelease, non-draft
  release, sorted by the created_at attribute." Published releases are readable without a token. Each asset has
  `name`, `size`, `url`, `browser_download_url` (and `digest`, `content_type`, …).
- Rate limit: "The primary rate limit for unauthenticated requests is 60 requests per hour", per originating IP
  address; headers `x-ratelimit-limit`, `-remaining`, `-used`, `-reset`; exceeding it answers 403 or 429. haetty uses
  one request a day (plus the manifest and its signature, which are asset downloads).
- Assets: "API clients should handle both a 200 or 302 response"; a `browser_download_url` (on `github.com`)
  redirects with 302 to `release-assets.githubusercontent.com` (checked once by hand with a public repository's asset;
  the signed query of the target was not logged). Older assets were served from `objects.githubusercontent.com`: both
  hosts are allowed.

## U1–U5. What was built

- `crates/haetty-update` (new): `manifest` (format 1; written by `haetty release-manifest`, read by the updater: one
  implementation), `version` (semver order), `sign` (minisign "ED" only; keys from `assets/update/haetty.pub`, empty
  now), `hash` (SHA-256), `archive` (tar.gz and zip in memory, named plain files only), `layout` (forms a–d, version
  folders, the link, prune, the single executable, Windows junctions through `DeviceIoControl`), `state` (the check
  schedule, the start guard, the window-up mark, the note), `flow` (check → download → install), `net` (ureq).
  Test-only (`test-support`, also turned on for its own tests by a self dev-dependency): the test key, the test CA and
  server, archive writers.
- `tools/release.sh` (the person's): see SELF-HOSTING "Releases". Inside a Claude Code session it stops before
  minisign and `gh` and prints the two commands; a commit instead of a tag is a dry run. It refuses a binary holding
  the TEST-ONLY key or CA.
- `tools/install-stable.sh` puts and activates versions through `haetty install-layout` when the built binary has it
  (the shell code stays only for builds before PU).
- The window (`updater.rs`, `app_settings.rs`): the updater thread, the Updates group, the button's text colour, the
  palette's "Updates", Restart now / Later / Roll back, the start guard (`main`), the restart after the window closed
  (`main` → `updater::restart_after_close`).
- `haetty update --check [--json]`; any other `update` option is refused ("installed only from the settings panel").

### Found and fixed while testing

- The restart first waited for the daemon by connecting to it every 250 ms — each connection kept the daemon busy,
  so it never reached its idle exit. It now watches the daemon's PID (`wait::pid_ended`), and the window's own
  connection is dropped (the app is dropped) before the wait.
- The restart's watch rolled back a new version whose window had started and then closed by itself (its one tab
  ended): only a version that never got as far as its window (`state::mark_up`) is rolled back now; a crash after the
  window shows is caught by the start guard at the next start.
- `release.sh` built only `haetty` (`--bin haetty` applied to both packages): both `--bin`s are named now.

## U6. Checks

- **Unit** (`cargo test -p haetty-update`, in the gate): manifest round trip and refusals, 20 000 mutated manifests
  (no panic; what parses round-trips), versions, SHA-256 (FIPS vectors incl. a million `a`), the archive reader
  (escapes, links, hard links, duplicates, missing files; 6 000 mutated or random archives without a panic), the
  layout (read-only folders, never overwritten, atomic link, a real file at the link refused, detect a/b/c/d, prune),
  the single-file form and its rollback, the state files, the test key (good, changed data, another key, none, the
  legacy unhashed form).
- **The case table against a local HTTPS server** (`crates/haetty-update/tests/update.rs`): a newer signed release
  installs and switches the link, only the release's three paths asked for; then, each with the layout unchanged and
  no partial file left: no newer version; an older version signed again; a wrong signature; no signature; another
  key; a changed manifest; the asset's sha256; its size; too old for an in-app update; a redirect to another host;
  an archive that escapes; an archive with a link. A download broken off after 5000 bytes resumes with
  `Range: bytes=N-`; a server that answers after 3 s times out at the 1 s limit; a closed port fails at once; `http://`
  and other hosts are refused before connecting; a full disk (`/dev/full`) and a read-only versions folder install
  nothing; a dev or cargo build is refused; the single-file form replaces and refuses a new file reporting another
  commit.
- **GUI**: the Updates group (first while an update is out; Restart and Roll back take two presses; with a
  permission wait the first press selects Later), and a source test that update actions are reached only from the
  panel's key and click handlers (which only winit's keyboard, IME and mouse events call), that the protocol has no
  update message, and that `haetty update --apply` is refused. Reference frames `claude-gear-update`,
  `settings-updates` (Linux).
- **Xvfb end to end** (`scripts/e2e/update.sh`, isolated HOME, two `update-test` builds 0.90.0 and 0.90.1 of this
  tree, the fake server): **19 of 19** — 0.90.0 installed as a version folder and link; the check finds 0.90.1;
  Download and install puts 0.90.1 beside 0.90.0 (read-only), the link moves, the running window is untouched;
  Restart now closes the window, waits for the daemon, starts 0.90.1 with the tab back; confirmed after 20 s; Roll back
  returns to 0.90.0; 0.90.2 (ends at once) is found, installed, started, noticed within 20 s and rolled back by itself,
  the reason kept for the panel; form (b): the single executable replaced, the old one beside it; the real
  `~/.local/opt/haetty`, `~/.local/bin/haetty` and the stable haetty processes (PIDs and start times) as before.
  Not exercised: an older daemon of another protocol (both builds speak 12) — the new window's message for it is
  untested.
- **Start time and drawing with a check that hangs** (`scripts/e2e/update-timing.sh`, a server that accepts and stays
  silent, the check started at once): start to window shown, 5 runs: median 537 ms (check off) vs 540 ms (hanging);
  draw time while typing 73 characters: median 140 µs vs 142 µs, p95 193 µs vs 191 µs. The check runs on its own
  thread; nothing on the window's thread waits for the network.
- **Installer self-test** (`tools/test-install-stable.sh haetty-v0.3.2 db952d4`): 19 of 19 — `db952d4` installed
  through `haetty install-layout`, 0.3.2 (no `install-layout`) through the shell fallback; rollback, reinstall,
  cleanup, the real prefix refused, the real `~/.local` unchanged.

## U1. Reproducibility (two dry runs of `db952d4`, separate target folders)

`HAETTY_RELEASE_TARGET=…/t1` and `…/t2 tools/release.sh db952d4 --out …`:

| asset | run 1 | run 2 |
|---|---|---|
| `haetty-0.3.2-x86_64-linux.tar.gz` | `12105d29244bc7b2…` | `12105d29244bc7b2…` — **identical** |
| `haetty-0.3.2-x86_64-windows.zip` | `df1207e81a2bb6f1…` | `77e7a10b912f4aff…` — differs |

The Windows difference is in the executables themselves (`haetty.exe` differs in about 398 000 bytes spread through
the file, `haetty-headless.exe` too). Not the build paths (neither target folder's path is in the binaries; the
source paths are remapped) and not the PE timestamp (the same in both). The Linux build of the same commit with the
same flags is byte-identical, which points at the mingw link step or the resource compiler; **cause not found** in
this stage. The manifest differs only by that asset's sha256. Releases are still checked by the signed sha256 of what
was uploaded, so this does not weaken updates; it only means a second build cannot confirm a Windows asset.

## Choices made, and what was not chosen

- **ureq 3, one client, two TLS backends** (Linux rustls/ring + system store, Windows Schannel): U0's smallest
  compliant choice per target. Not chosen: rustls on Windows too (+1 MB there, one code path), aws-lc-rs (larger, C),
  minreq/attohttpc (larger), bundled root certificates on Linux (27 KB smaller but frozen at build time).
- **No archive or hash crates**: tar/zip readers of ~250 lines on the inflate the binary already has, and SHA-256 in
  `hash.rs`. Not chosen: `flate2`+`tar` (+120 KB), `zip` (+234 KB), `sha2` (+12 KB; a dependency outside the approval).
- **Archives read in memory** (a release is ~10 MB): no half-extracted files on disk; the size limit is 128 MB a file.
- **Restart without a new daemon message**: the window closes as with its close button and the daemon's idle exit is
  awaited by PID (up to 15 s). Not chosen: a "shut down" message (a change of `Daemon::message`'s role table, a stop
  condition of this stage).
- **The start guard uses two signals**: the window-up mark (the restart's watch rolls back a version that never
  showed its window) and the pending file's start count (the next start rolls back a version that showed its window
  and then died within 20 s). Not chosen: rolling back on any quick exit (a restored tab that ends closes a one-tab
  window by design).
- **`install-layout` and `release-manifest` are subcommands of haetty itself**: the shell scripts call the same Rust
  code the in-app update uses; `install-layout` never downloads. `haetty update` has `--check` only.
- **A shell-only window reaches the Updates group through the palette** (built). The alternative — a dim `↑` at the
  tab bar's right end while an update is out — is only a dump: `docs/look/pu-update-mark-a-palette.png` (built) and
  `pu-update-mark-b-tabbar-arrow.png` (mock) — **for the person to choose**.
- **`min_update_from` defaults to 0.0.0** in `release.sh` (no restriction); `--min-update-from V` raises it.
- **Test builds** (`--features update-test`) trust the TEST-ONLY key and CA, may check under `HAETTY_TEST_TMP`
  (`HAETTY_UPDATE_TEST=1`), and may shorten and force the first check (`HAETTY_UPDATE_TEST_FIRST_MS`); the version
  a build reports may be set at build time (`HAETTY_BUILD_VERSION`, only the e2e uses it). `release.sh` refuses a
  binary that holds the TEST-ONLY key or CA.
