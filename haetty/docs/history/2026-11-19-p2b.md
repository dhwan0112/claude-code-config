## Choices (the rule "closest to the four points")

- **The worker of `task new` is detached.** DESIGN §2: events never change the layout, and a coordinator's command is
  an event for the window. The person opens it with one click on its line in the sidebar's Workers (or "Attach
  detached sessions"), which is needed anyway: Claude Code's folder-trust question is the person's. Alternative: open a
  tab at once (fewer clicks, against §2).
- **The CLI creates the session itself** over a short Control connection (no change to the role checks: `Create` and
  `SetObservable` were Control messages already), with the spec the GUI would give (config theme, scrollback, engine,
  integration, saving mode), at 120×36 until a window attaches it. Alternative: a request file the GUI acts on (a
  second path into the GUI, and still an event that changes the layout).
- **The worker's environment** is the command's, without Claude Code's child markers (as the GUI does) and without the
  coordinator tab's proxy variables and folder: a worker is not a child of the coordinator.
- **The sidebar polls** the task folder and the daemon's session list every 3 s, only while it shows Workers (the Log
  is read every 5 s the same way). No new protocol message.
- **`background` is a separate count** beside `turns` in `ClaudeInfo` and `SessionInfo`; the attention mark and the
  input hold do not read it (the permission-prompt path is unchanged). Claude Code 2.1.327's hook schema
  (`background_tasks`: "In-flight background work (running/pending + backgrounded) … Empty array when nothing is in
  flight"; items `{id, type: shell|subagent|monitor|workflow, status, description, …}`) was read from the installed
  binary's strings, not run.
- **`wait worker`** looks once a second over an observe-only connection; the first look is the baseline; a task made
  after the start gets its own baseline (a new task is not a change).
