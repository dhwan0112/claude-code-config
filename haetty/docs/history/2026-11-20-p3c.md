## Protected areas

- **The settings haetty injects:** a Claude Code tab gets `CLAUDE_CODE_SSE_PORT`; a shell tab gets `HAETTY_IDE_PORT`,
  which the proxy passes on as `CLAUDE_CODE_SSE_PORT` only when it injects the integration. 13.5 decided the variable
  for a Claude Code tab; the proxy (stage PH) came after 13.5, and the shell tab is where most Claude Code now starts,
  so the same decision was applied there. Nothing else of the proxy or the injected settings changed.
- **The role checks (`Daemon::message`):** `IdeAnswer` falls in "everything else is Control's alone"; the handler
  also refuses any origin but `Human` ("IdeAnswer from a program"). An answer counts as the person's input (K1), as the
  stage text asks ("consistent with the permission-wait mark and the input-hold rules").
- **The permission-prompt path:** Claude Code's own dialog is unchanged and still answers; haetty never sends
  `TAB_CLOSED` (Claude Code takes it as an accept), and Esc closes the overlay without an answer.
- **§2:** the overlay opening by itself on a proposal (DESIGN 01 §2.1), the reference frame `ide-proposal`.

## Pitfalls hit

- An e2e script started from a Claude Code session that runs inside haetty inherits `HAETTY_PROXIED=1`: the dev
  instance's proxy then passes `claude` through unchanged (the recursion rule), so no port and no settings. `ide.sh`
  unsets `HAETTY_PROXIED`, `HAETTY_PROXY_DIR`, `HAETTY_CLAUDE_SETTINGS`, `HAETTY_SESSION_ID`, `HAETTY_IDE_PORT`.
- Claude Code 2.1.329's folder-trust question has "No, exit" selected first: a script answers with Down, Enter.

## Windows

Not on Windows: the daemon starts no server there (the prototype's token comes from `/dev/urandom`), so the setting
does nothing; `tests/ide.rs` and `ide.sh` are Unix only. PW line in HANDOFF.
