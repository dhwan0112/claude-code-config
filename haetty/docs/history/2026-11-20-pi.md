Known problems found (cited): `ZDOTDIR` set in `/etc/zshenv` bypasses the folder — both call it unsupported (kitty
#6330, Ghostty PR #9911); `exec zsh`, nested zsh, tmux, `sudo -E zsh` get no integration but inherit `PATH` (both
integration files' headers); Oh My Zsh and Prezto remove zle hooks, hence the deferral (kitty `kitty-integration`
74-80); powerlevel10k moves its own precmd last every prompt (p10k `internal/p10k.zsh` 7120-7121), so "be last"
hooks leapfrog it (Ghostty #11367, #14705); a `.zshrc` that empties `precmd_functions` removes the hook in both
(Ghostty PR #10709 discussion); `--posix` left `inherit_errexit` on (kitty #5349); Ghostty once clobbered the
user's `ENV` (PR #7908); bash 3.2 on macOS ignores `ENV` in POSIX mode (Ghostty PR #2966).

### Choice

- zsh as the stage text says (the method of both terminals, written anew): `ZDOTDIR` points at `<run dir>/zsh`
  (written by the daemon at start from `haetty-cc/src/shell/zshenv.zsh`, built into the executable); the person's own
  `ZDOTDIR` rides in `HAETTY_ZSH_ZDOTDIR` (present only when they had one; an empty value counts as set). The file
  restores `ZDOTDIR`, sources `${ZDOTDIR-$HOME}/.zshenv`, and in an interactive shell appends `_haetty_path_first` to
  `precmd_functions`. Not deferred and not "be last": the hook does not depend on order (it compares the first entry
  and rebuilds `path` with the folder first and every other copy removed), so it does not fight p10k's or direnv's
  hooks. zsh reads `.zprofile`, `.zshrc`, `.zlogin` itself in its own order: the startup-file order is unchanged
  (tested), so the stop condition did not apply.
- bash: not the `--posix`/`ENV` start of both terminals — it means haetty replaying bash's startup files in its own
  order and guessing system paths. Instead the simplest way that changes none of the person's files: the tab gets an
  exported function (`BASH_FUNC__haetty_path_first%%`, bash imports it) and `PROMPT_COMMAND` naming it first (before a
  `PROMPT_COMMAND` the environment had). Its limit: a `.bashrc` that assigns `PROMPT_COMMAND` without keeping the old
  value drops it (one that prepends, appends or uses the 5.1 array keeps it). The function keeps `$?`.
- Not done: fish and other shells (the sidebar's "without haetty's integration" lines stay); a shell command with
  arguments; `ssh` (the variables do not travel); worker tabs and `haetty task new` run claude directly.
- "No shell at run time" (CLAUDE.md): haetty runs no script; the `.zshenv` and the function are settings the person's
  own shell reads (DESIGN §13.8).

### Evidence

  test): zsh — a `.zshrc` that puts `~/.opencode/bin` and `~/.local/bin` first: at the prompt `PATH` starts with the
  proxy folder, which is on it once; `whence -p claude` and `whence -p haetty` are the proxy's (`haetty` links to the
  daemon's executable); `claude` typed in the tab ran the fake real claude with `--settings`; a line that puts
  `~/.local/bin` first runs with it and the next prompt moves the proxy back; `ZDOTDIR` unset as before; the order
  log reads `zshenv, zshrc` (`.zprofile`/`.zlogin` exist and are not read: not a login shell) — the same with `off`,
  where `PATH` stays the person's; arguments (`zsh -i`): left alone; the person's `ZDOTDIR`: its `.zshenv` and
  `.zshrc` are read, the home's `.zshenv` is not, `ZDOTDIR` is theirs at the prompt; a `.zshenv` that sets `ZDOTDIR`:

## I2. The sidebar from the keyboard

- Ctrl+Shift+E (`focus_sidebar`; free in Claude Code, whose Ctrl+E is "end of line"; §3.11): the docked sidebar takes
  the keyboard — ↑/↓, ←/→ fold, Enter as a click (Files → the diff, Agents → the record, Workers → the tab or the
  detached worker), Esc, the key again or a click in the terminal gives it back. Meanwhile keys, the paste action and
  input-method text never reach the program; actions bound to chords (new tab, palette …) still run. Without a docked
  sidebar the key opens it over the terminal (the overlay, which has always had the keyboard). An action that opens
  something (diff, record, a worker's tab) ends the focus; the sidebar never has the keyboard while the diff overlay
  or a record is open.
- The mark (DESIGN §2.1, approved): `›` before the selected line, its text in the normal grey (a section title loses
  its brighter step); no accent, no underline. The overlay used the strong grey and an underline before; it now uses
  the same mark. New reference frame `sidebar-focus` (Linux); Windows frames wait for PW.
- `tests/permission.rs` `the_sidebar_taking_the_keyboard_leaves_the_question_and_the_hold`: with a question pending,
  the sidebar's queries (`ListSessions`, `GetClaude`, `GetSessionLog`, `GetEdit`) three times: `Ask` stays and a
  program's write is still refused; the person's key afterwards answers. No code changed on that path: the focus is
  the window's alone and sends the daemon nothing.
- `scripts/e2e/sidebar.sh`: "Ctrl+Shift+E: typed text did not reach the program", "Esc: the terminal has the keyboard
  again". Dump `docs/look/pi-sidebar-focus.png`.
- Full paths: git's changes in a shell tab and the git views' file lists are joined to the repository's folder; the
  match is exact (separators aside); names are shown from the repository's folder. Unit tests (the same tail in two
  worktrees is two files); `diff.sh` 26/26.
