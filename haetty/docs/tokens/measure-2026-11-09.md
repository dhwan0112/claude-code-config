## What this says

1. **The context is the cost.** 99 % of the tokens are cache reads of the context. A large result that stays in the
   context is paid again on every later response, so keeping results short saves more than any single response.
2. **Stale paths.** Six of the 20 results in the two top-10 lists read the old `ccterm/` copy, from before the rename
   to haetty (2026-11-05). The likely source is the memory note `ccterm_repo_location`, which names `claude-code-config/
   ccterm` as the repository; the transcript does not show it directly. Fix the note, not the tool.
3. **Session-start documents.** DESIGN.md was read whole (42 KB, about 10,500 tokens), and HANDOFF (31 KB) twice in the
   main top 10. Stage G0 cut the session-start total from 45.7k to 12.3k estimated tokens (DESIGN is now an index).
4. **Generated build output.** Four of the subagents' top 10 read files under `target/` (the libghostty build). The
   search and read guidance should exclude `target/`.
5. **Whole-file reads.** Source files are read whole (33–46 KB each) where a range or a grep would do.
6. **Saved outputs read back.** A saved tool output (31 KB) and a background task's output (29 KB) were read into the
   context. `haetty run` (stage G2) keeps such output in a log and prints only the summary.
7. **One web page** of 46 KB was fetched whole.

## Limits of this measurement

- One development session and its subagents; no other haetty session is in the local transcript store.
- Sizes are bytes of text. The token counts are the API's `usage` numbers, which are exact; the attribution of a
  response to the preceding tool is an approximation (a response depends on its whole context).
- The report cannot tell which result a cache read is for: it is the context of the response, so the per-tool sums show
  where the context came from, not what each result cost.
