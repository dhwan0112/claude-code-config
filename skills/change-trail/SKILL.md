# 변경 추적

코드에 주석을 두지 않으면 "왜 이렇게 됐는가"는 이력이 답해야 한다. 이력은 변경과 묶여 있어 낡지 않고, 다음 에이전트가 선례로 베끼지도 않는다. 이 스킬은 그 이력이 실제로 읽을 만하게 남도록 한다.

## 정보별 위치

| 남기려는 것 | 위치 |
|---|---|
| 이 코드가 무엇을 하는가 | 이름, 함수 추출, 타입 |
| 왜 이렇게 바꿨는가 | 커밋 메시지 본문, PR 설명 |
| 하면 안 되는 것 | 타입, 런타임 검사, 테스트, 린트 규칙 |
| 남은 일 | 이슈 트래커. 코드에 남겨야 하면 이슈 번호 포함 |
| 설계 결정과 버린 대안 | 결정 로그 또는 ADR |
| 시스템이 어떻게 동작하는가 | 저장소 문서 (구조 문서, 기능 지도) |

## 커밋

- 변경 하나에 커밋 하나. 각 커밋은 그 자체로 빌드되고 검증 가능해야 한다
- 리팩터링과 동작 변경을 한 커밋에 섞지 않는다
- 제목에는 무엇을, 본문에는 왜를 적는다. 코드를 읽으면 알 수 있는 내용은 본문에 반복하지 않는다
- 버린 대안이 있으면 한 줄로 적는다
- 우회책을 넣었다면 원인, 제거 조건, 관련 이슈를 본문에 적는다. 이 정보가 주석 대신 있어야 할 자리다
- 주석이나 억제를 지웠다면 왜 더 이상 필요 없는지 적는다
- PR 없이 기준 브랜치에 바로 커밋하는 저장소에서는 커밋 본문이 PR 설명의 일을 한다. 무엇을 돌려 무엇을 확인했는지, 확인하지 못한 것은 무엇인지 적는다
- 저장소에 커밋 규약이 있으면 그것이 우선한다

## PR

- 되돌리기 쉬운 크기로 쪼갠다. 큰 작업은 순서대로 쌓이는 작은 PR 여러 개로 나누고, 각 PR이 검증으로 끝나게 한다
- 설명에는 목적, 접근, 검증 방법과 결과를 적는다. 검증은 "했다"가 아니라 무엇을 돌려 무엇을 확인했는지 적는다
- 범위 밖이라 하지 않은 일과 알려진 한계를 적는다
- 커밋과 푸시는 사용자가 요청했거나 저장소 지시 파일이 미리 허용한 범위에서만 한다

## 결정 로그

여러 단계에 걸친 작업이나 사용자가 지켜보지 않는 자율 작업에서는 결정을 파일로 남긴다. 저장소에 이미 정해진 위치나 형식(ADR 등)이 있으면 그것을 따르고, 없으면 `docs/decisions.tsv`에 탭 구분으로 다음 열을 쓴다.

`날짜  범위  결정  근거  버린 대안  검증 방법`

- 한 줄에 결정 하나
- 나중에 "왜 이렇게 했지"라고 물을 만한 것만 적는다. 사소한 구현 선택은 제외한다
- 근거에는 확인한 사실을 적고, 추측이면 추측이라고 적는다
- 결정을 뒤집으면 기존 줄을 고치지 말고 새 줄을 추가해 무엇을 대체하는지 적는다
- 로그를 커밋할지는 사용자 방침을 따른다

## 이유를 찾을 때

주석이 없는 코드의 이유가 필요하면 추측하지 말고 이력에서 찾는다.

1. `git blame`으로 해당 줄의 커밋을 찾는다
2. `git log -S '<문자열>'` 또는 `git log -L`로 그 코드가 들어오고 바뀐 경위를 따라간다
3. 커밋 본문, 연결된 PR, 이슈, 결정 로그를 읽는다
4. 찾은 근거는 출처(커밋 해시, PR 번호)와 함께 보고한다. 이력에서 근거를 찾지 못했으면 찾지 못했다고 말한다
