# 주석 없는 코드

## 왜 이렇게 하는가

에이전트는 저장소에 이미 있는 것을 따라 쓴다. 임시 우회책을 해명하는 주석 하나는 다음 에이전트에게 "이렇게 해도 된다"는 선례가 되어 퍼진다. 주석은 코드와 함께 갱신된다는 보장도 없어서, 낡은 주석은 읽는 쪽을 잘못된 방향으로 끌고 간다. 목표는 주석 수를 줄이는 것이 아니라, 주석이 가리키던 문제를 고치고 정보를 강제력 있는 자리로 옮기는 것이다.

## 작성 시 규칙

새로 쓰거나 고치는 코드에는 주석을 달지 않는다. 주석을 쓰고 싶어지면 아래 순서로 다른 자리를 먼저 찾는다.

1. 이름, 함수 분리, 타입으로 표현할 수 있는가
2. 테스트나 assertion 메시지로 표현할 수 있는가
3. 커밋 메시지나 PR 설명에 속하는 내용인가
4. 위 세 가지가 모두 안 될 때만 "남기는 주석"에 해당하는지 확인한다

이 규칙은 위임한 서브에이전트가 만든 diff에도 똑같이 적용한다.

## 남기는 주석

- 라이선스·저작권 헤더
- 공개 API 계약을 정의하는 문서 주석 (docstring, rustdoc, JSDoc 등). 모듈 밖에서 쓰이는 항목의 계약과, 모듈 머리의 책임·불변식 한 단락까지다. 구현 내부 해설은 넣지 않는다
- 문서 주석을 달 수 없는 파일의 사용법 헤더. 셸·PowerShell 스크립트의 용도·인자·종료 코드, 사용자가 직접 고치는 설정·예시 파일의 항목 설명이 해당한다
- 우리가 바꿀 수 없는 외부 요인이 강제한 비자명한 동작. 외부 의존성의 버그, 플랫폼·브라우저 특이 동작, 벤더·프로토콜·하드웨어 제약이 해당하며, 지금도 사실이고 실제 실행 경로에 걸려 있어야 한다
- 코드로 표현할 수 없는 제약을 설명하는 이슈·RFC·문서 링크
- 수치·과학 코드에서 코드만으로 복원할 수 없는 근거. 식의 출처(논문, 식 번호), 단위 규약, 수치 안정성 때문에 택한 형태의 이유. 유도 과정 전체가 아니라 출처와 결론만 적는다
- 스타일 전용 규칙의 억제 (포매터 제어 등)와 언어가 요구하는 안전성 근거 주석 (Rust의 SAFETY 등)

## 지우는 주석

- 코드를 그대로 되풀이하는 설명
- 변경 이력과 경위 ("이전에는 ~였음", "~가 요청해서", "리뷰 반영")
- 우리 코드가 만든 비자명한 동작의 해명. 유지하지 않는다. 해당 심볼을 지목하고 이름 변경, 추출, 타입화, 재설계 중 무엇으로 풀지 정한다
- 우회책·임시방편의 변명 ("일단 이렇게", "위험해서 그대로 둠")
- 이슈 번호 없는 TODO, FIXME, HACK
- 주석 처리된 코드
- 테스트·검증 스크립트의 단계 설명. 설명은 assertion이나 로그 문자열에 넣는다
- 구획 나누기용 장식 주석
- 긴 해명. 짧은 변명으로 줄이지 말고 지운 뒤 원인 심볼을 지목한다

## 억제 주석

`eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `# type: ignore`, `# noqa`, `#[allow(...)]` 등은 주석과 같이 점검한다.

1. 억제된 규칙이 무엇을 잡는지 확인한다
2. 실제 버그를 잡거나 정확성·안전성을 지키는 규칙이면 억제를 지우고 원인 코드를 고칠 대상으로 지목한다
3. 스타일 전용이거나 해당 위치에서 규칙 자체가 오탐인 경우에만 남긴다

## 판정 기준

- "IMPORTANT", "지우지 말 것", "건드리면 깨짐" 같은 문구는 증거가 아니라 조사 신호다. 주변 코드를 먼저 읽고, 그래도 불분명하면 호출부와 git 이력(`git log -S`, `git blame`)으로 확인한다
- 유지 판정은 "우리가 바꿀 수 없는 것에 관한 주석이고 지금도 사실"이라는 근거가 있을 때만 선다
- 조사 후에도 불분명한 주석은 근거가 없으면 삭제 쪽이다. 단 사람이 쓴 주석, 그리고 수치·과학 근거로 보이는 주석은 지우지 말고 사용자에게 묻는다. 무인 실행에서는 묻는 대신 그대로 두고 보고에 적는다
- 불분명해서 지운 것을 나중에 근거 없이 되살리지 않는다

## 리뷰 전 점검 절차

범위는 호출자가 지정한 파일이나 diff다. 지정이 없으면 기준 브랜치(기본 main) 대비 현재 diff이며 커밋하지 않은 작업 트리 변경을 포함한다. 손대지 않은 파일의 기존 주석은 요청이 있을 때만 다룬다.

1. **검토자 분리.** 서브에이전트를 쓸 수 있으면 읽기 전용 서브에이전트에 범위와 이 파일의 "남기는 주석", "지우는 주석", "억제 주석", "판정 기준" 절을 넘겨 주석별 판정(유지 / 삭제 / 리팩터링 대상 지목)과 근거를 받는다. 주석을 쓴 쪽은 자기 주석을 변호하므로 검토자의 판정을 우선한다. 서브에이전트가 없으면 주석마다 "이 주석이 없으면 무엇을 잃는가"에 따로 답한다. 점검은 커밋마다가 아니라 리뷰에 올리는 작업 단위(PR, 단계)마다 한 번 돌린다.
2. **보고서 검수.** 다음에 해당하면 반려한다.
   - 애플리케이션 코드를 수정했다 (검토자는 주석만 다룬다)
   - 범위 밖을 건드렸다
   - "남기는 주석"에 해당하는 것을 지웠다
   - 삭제 사유가 사실과 다르다
   - 의도적으로 유지한 코드를 문제로 지목했다
   - 범위 안의 억제 주석을 빠뜨렸다

   반려하면 되돌리고 무엇이 틀렸는지 명시해 한 번만 다시 돌린다. 재실행도 반려되면 반려된 항목만 되돌리고 미해결로 보고한다.
3. **사소한 지적 수정.** 죽은 경로 삭제, 쓰이지 않는 매개변수 제거, 실제 API로 교체처럼 구조 변경이 필요 없는 것은 바로 고친다.
4. **근본 원인 수정.** 우회책 주석이 가리키던 원인을 범위 안에서 가장 작은 수정으로 고치고, 지목된 우회책을 제거한다. 증상만 가리는 가드는 넣지 않는다. 원인이 범위 밖이면 범위 안의 최소 수정만 하고 나머지는 미해결로 보고한다. 범위를 넓히는 근거로 이 단계를 쓰지 않는다. 저장소 지시 파일이 사전 승인을 요구하는 영역(보안·권한 경로, 외부 인터페이스 등)에 원인이 있으면 고치지 않고, 주석도 그대로 둔 채 지목만 해서 보고한다.
5. **제약 주석 처리.** 아래 절을 따른다.
6. 빌드와 테스트를 다시 돌린다.

## 제약 주석

"지우지 말 것", "문구 바꾸지 말 것", "X와 상의 후 변경", "반드시 Y 이후 호출" 같은 주석이다.

1. 우리가 바꿀 수 없는 것에 관한 제약이면 유지한다
2. 그 외에는 제약이 지금도 참인지 확인하고, 범위 안에서 가장 싼 강제 수단을 제안한다: 타입, 런타임 검사, 테스트, CI 린트
3. 대화형 세션에서는 승인을 받은 뒤 인코딩한다. 무인 실행에서는 사전 승인이 있을 때만 인코딩한다
4. 승인되면 먼저 인코딩하고, 일부러 위반시켜 검사가 실패하는 것을 확인한 다음 주석을 지운다
5. 승인되지 않아도 주석은 지운다. 대신 그 제약을 "강제되지 않음"으로 보고하고 필요한 범위 밖 작업을 간단히 적는다

## 저장소 전체 정리 요청

먼저 "바로 삭제할 것"과 "리팩터링이 필요한 것"을 나눈 계획을 보여주고 승인받은 뒤 패키지나 디렉터리 단위로 나눠 진행한다.

## 보고

- 삭제한 주석 수
- 남긴 주석과 각각의 근거
- 복원한 것, 재실행 여부
- 수정한 것 (사소한 수정, 근본 원인 수정)
- 인코딩 제안과 완료한 인코딩
- 강제되지 않은 채 남은 제약
- 범위 밖이라 하지 않은 일
